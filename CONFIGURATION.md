# Alpha — configuration reference

Every value, where it comes from, where it goes. Extracted from
`src/config/env.ts`; [SETUP.md](SETUP.md) has the procedure.

Three places get configured — **Render** (cloud API), **Vercel** (web app) and
each **developer's machine** (desktop app) — and they want different things,
because the cloud half and the desktop half have opposite jobs.

---

## Where each value comes from

```
GitHub App  ──┬─ Client ID          ─┐
              ├─ Client Secret       │
              ├─ App ID              ├──> RENDER
              ├─ Private key .pem    │
              ├─ Webhook secret      │
              └─ App slug           ─┘

Supabase    ──┬─ Project URL        ──> RENDER + VERCEL
              ├─ anon key           ──> RENDER + VERCEL
              └─ JWT Secret         ──> RENDER only

Render      ──── service URL        ──> VERCEL (as VITE_API_URL)
                                    ──> GitHub App (callback + webhook)

Vercel      ──── app URL            ──> RENDER (as CORS_ORIGIN)
                                    ──> GitHub App (homepage)
```

The loop between Render and the GitHub App is why SETUP.md says to create the
App with placeholder URLs and correct them after the first deploy.

---

## 1. GitHub App

One App. The first three rows are the login half; the rest is the server half.

| Setting | Value |
| :--- | :--- |
| Callback URL | `https://<render>.onrender.com/api/github/oauth/callback` |
| Request user authorization (OAuth) during installation | **checked** |
| Expire user authorization tokens | **unchecked** |
| Homepage URL | `https://<vercel>.vercel.app` |
| Webhook URL | `https://<render>.onrender.com/api/github/app/webhook` |
| Webhook secret | `openssl rand -hex 32` |
| Where can this be installed | Only on this account |

**Permissions**

| Scope | Permission |
| :--- | :--- |
| Repository → Contents | Read & write |
| Repository → Pull requests | Read & write |
| Repository → Actions | Read & write |
| Repository → Issues | Read & write |
| Repository → Metadata | Read |
| Organization → Members | **Read** |

Then install on the organisation, all repositories.

## 2. Render — the cloud API

`render.yaml` sets the first three. The rest are prompted for. Nothing
deployment-specific is written in the repository — no org, hostname or ID has a
default in code, so each deployment names its own.

### Set automatically

| Variable | Value | Why |
| :--- | :--- | :--- |
| `ALPHA_MODE` | `cloud` | Disables the runner, runtime discovery, local scaffolding and the raw WebSocket |
| `ALPHA_SESSION_SECRET` | generated by Render | Encrypts stored GitHub tokens. **The daemon exits without it** |
| `healthCheckPath` | `/api/health` | — |

### Prompted for

| Variable | Source | Required |
| :--- | :--- | :---: |
| `ALPHA_ORG` | your GitHub organisation's login | yes — **the daemon exits without it** |
| `GITHUB_CLIENT_ID` | App → Client ID | yes |
| `GITHUB_CLIENT_SECRET` | App → generate a client secret | yes |
| `GITHUB_CALLBACK_URL` | `https://<render>.onrender.com/api/github/oauth/callback` | yes |
| `GITHUB_APP_ID` | App → App ID | yes |
| `GITHUB_APP_PRIVATE_KEY` | the whole `.pem`, `BEGIN`/`END` lines included | yes |
| `GITHUB_APP_SLUG` | from the App URL, e.g. `alpha` | yes |
| `GITHUB_APP_WEBHOOK_SECRET` | the secret you generated | yes |
| `SUPABASE_URL` | Supabase → Settings → API | yes |
| `SUPABASE_ANON_KEY` | Supabase → Settings → API | yes |
| `SUPABASE_JWT_SECRET` | Supabase → Settings → API → JWT Secret | yes |
| `CORS_ORIGIN` | the Vercel origin | yes |
| `ALPHA_ADMINS` | `LloydLim1` | temporary |

### Never set on Render

| Variable | Why |
| :--- | :--- |
| `PORT` | Render supplies it |
| `HOST` | Cloud mode binds `0.0.0.0`; a loopback value is overridden and logged |
| `SQLITE_DB_PATH` | Cloud mode should not be using SQLite |
| `ALPHA_HOME` | Ephemeral disk; nothing there survives a deploy |
| service_role key | Bypasses every RLS policy. Nothing in Alpha uses it |

### Optional, with working defaults

| Variable | Default | Change it when |
| :--- | :--- | :--- |
| `SESSION_TTL_MS` | `604800000` (7 days) | You want shorter browser sessions |
| `SUPABASE_TOKEN_TTL_MS` | `600000` (10 min) | Rarely — un-revocable, so short is the point |
| `GITHUB_SCOPE` | `repo,workflow,read:org` | Before showing a real client, to narrow the consent screen |

### CORS_ORIGIN

```
https://alpha-fe-main.vercel.app
```

Preview deploys need a pattern that pins a label you control:

```
https://alpha-fe-main.vercel.app,https://alpha-fe-main-*-lloyds-projects.vercel.app
```

A bare `https://*.vercel.app` is **refused at parse time and logged**. The apex
is shared, so that pattern is every tenant on Vercel, and the API sends
credentials.

## 3. Vercel — the web app

| Variable | Value |
| :--- | :--- |
| `VITE_API_URL` | `https://<render>.onrender.com/api` — note the `/api` |
| `VITE_SUPABASE_URL` | same as Render's `SUPABASE_URL` |
| `VITE_SUPABASE_ANON_KEY` | same as Render's `SUPABASE_ANON_KEY` |

Deliberately unset:

| Variable | Why |
| :--- | :--- |
| `VITE_WS_URL` | The raw WebSocket is not created in cloud mode — it broadcasts every run to every client with no auth on upgrade. Realtime carries the same telemetry under RLS |
| `VITE_ALPHA_LOCAL_TOKEN` | Desktop only |

The anon key is public by design. It grants nothing alone: every table has RLS,
and the policies read claims from a token the API mints per session.

## 4. A developer's machine — the desktop app

`alpha-be-main/.env`, and most of it is already right by default.

| Variable | Value | Note |
| :--- | :--- | :--- |
| `ALPHA_MODE` | `desktop` or unset | Desktop is the default |
| `ALPHA_ORG` | same as Render | **Required** — the daemon exits without it |
| `HOST` | `127.0.0.1` | Loopback matters: this API spawns shell commands |
| `PORT` | `3001` | — |
| `CORS_ORIGIN` | `http://localhost:3000,http://localhost:5173` | — |
| `SUPABASE_URL` | same as Render | For the board uplink |
| `SUPABASE_ANON_KEY` | same as Render | — |
| `SUPABASE_JWT_SECRET` | same as Render | Without it, cloud writes carry no identity and RLS rejects them |
| `ALPHA_LOCAL_TOKEN` | optional | Set it if anything else on the machine could reach port 3001 |

**Never on a developer machine:** `GITHUB_CLIENT_SECRET`, `GITHUB_APP_PRIVATE_KEY`,
`ALPHA_SESSION_SECRET`. Those are server credentials, and a private key inside a
shipped `.exe` cannot be un-distributed. `githubService` warns at startup if it
finds them.

Identity on the desktop comes from `gh auth login` — no OAuth, no cookie, no
sign-in screen.

## What breaks without each one

| Missing | Symptom |
| :--- | :--- |
| `ALPHA_SESSION_SECRET` | Process exits at boot with an explanation |
| `ALPHA_ORG` | Process exits at boot with an explanation, in both modes |
| `GITHUB_CALLBACK_URL` | Sign-in screen shows "not configured" — there is no fallback address |
| `GITHUB_APP_SLUG` | The App install link is omitted rather than pointing at a 404 |
| `CORS_ORIGIN` | No browser origin is allowed; the web app's requests are blocked |
| `SUPABASE_JWT_SECRET` | Cloud writes rejected by RLS; logged once |
| `GITHUB_CLIENT_ID` | Sign-in screen renders "not configured" instead of a dead button |
| `GITHUB_CALLBACK_URL` wrong | Sign-in returns `#alpha_error=oauth_failed` |
| `CORS_ORIGIN` missing the Vercel origin | Every request blocked in the browser console |
| `ALPHA_MODE` not `cloud` on Render | Runner and filesystem scans start and find nothing forever |
| `HOST` set to loopback on Render | Overridden to `0.0.0.0`, with the reason logged |
| `ALPHA_ADMINS` cleared before the `admins` team exists | Nobody can manage members |

---

## After the `admins` team exists

Delete `ALPHA_ADMINS` from Render. It was a bridge for the window where no team
mapped to `admin` and the old `?? 'admin'` fallback had been removed — and a
way back in if reading teams is itself what broke.
