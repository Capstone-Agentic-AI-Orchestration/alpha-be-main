# Client landing and password accounts

This change is separate from the nine-phase ticketing plan, which is on hold.
The previous frontend remains a read-only visual reference. Its `dev_update`
branch contains the marketing and client-auth designs; its main working files
are a Next.js starter. Alpha continues using its existing Vite/React app.

## Workflow

Landing → existing inquiry form → PM review/invitation → verify invited email →
choose password → existing ticket-scoped client portal. Returning clients use
email/password; existing passwordless clients use password recovery to set a
password on their original Supabase identity.

The public inquiry contract, PM/developer GitHub authentication, project preview
permissions, messages, documents and packaged desktop entry remain unchanged.
The browser root shows the landing page; `/#/team` opens the staff entry, and
existing OAuth callback fragments still open the staff entry. `file:` always
opens the desktop's internal app.

## Server boundaries

- Supabase Auth stores/verifies passwords. Alpha never stores or logs them.
- `/api/client/auth/sign-in` validates password and existing active ticket access,
  then issues the existing HttpOnly Alpha client cookie.
- `/auth/setup/link` verifies a one-time invite/magic-link/recovery proof and
  creates a 15-minute, server-backed setup context. It cannot change the invited
  email, issue a portal session or grant ticket access.
- `/auth/setup` resumes that context after a browser refresh. Credentials are
  scrubbed from the URL before the exchange and are never in browser storage.
- `/auth/setup/complete` requires the setup cookie, its own CSRF token and the
  password. First setup and recovery update the password. An already-passworded
  account must supply its existing password to accept another invitation.
- Setup proofs are encrypted with a purpose-separated key derived from the
  existing server session secret. A database lease prevents concurrent reuse.
  Successful/superseded/expired contexts discard the stored proof; expired
  contexts are cleaned when subsequent setup contexts are created.
- Provider calls run outside database transactions. If a password save succeeds
  before a response is lost, retry authenticates that password rather than
  creating another identity or replacing an existing password.
- Password changes revoke Alpha's separate client sessions before updating the
  provider password. Setup/recovery never reactivates a revoked access grant.
- Legacy email-link API routes stay available during the frontend transition;
  the new frontend sends existing invitation URLs through password setup.
- Unknown recovery addresses receive the same response as eligible addresses.

## Deployment order

1. Apply `20261015111244_ticket_client_account_setups.sql` before deploying the
   new backend endpoints. It adds one private RLS-protected table and indexes;
   it does not alter Supabase Auth or existing business records.
2. Deploy the backend, then the matching frontend. The backend additions do not
   remove the previous frontend's endpoints. Rollback of the frontend leaves
   the additive private table harmlessly in place.
3. Existing Supabase keys, session secret, allowed web origin, Resend sender and
   Vercel same-origin API proxy are reused. Recovery proof is generated by
   Supabase and the email is sent through the existing Resend provider.
4. Test with an approved address: invite → setup → portal → logout → password
   login → password recovery. Verify old client cookies stop working after a
   reset and all previously granted requests still belong to the same identity.

No database migration, hosted configuration change, real email, deployment,
desktop release, commit or push is performed by preparing this branch. Automated
tests use the real PostgreSQL schema/queries and simulated provider/email calls.

## Regression results

- Backend: 163 test files, 2,688 tests passed; TypeScript check and build passed.
- Frontend: 28 test files, 320 tests passed; TypeScript/production build passed.
- Account regression covers original-identity reuse, an additional invitation,
  passwordless-account migration, password reset/session revocation, failed
  credentials, mismatched identity, expiry, CSRF and a lost provider response
  including invalidation of the original provider credential.
- Browser checks use compiled frontend assets with intercepted, simulated APIs:
  desktop/mobile layout, returning login, locked invited email, token scrubbing,
  refresh/resume, confirmation, CSRF, recovery and failed-setup handling.
- Live Supabase/Resend end-to-end verification is still required after the
  migration and matching deployments. Simulated providers are not live email
  delivery evidence. The existing internal-app bundle-size warning remains.
